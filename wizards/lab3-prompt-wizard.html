实验三 · RAG 技术背景

先认识 RAG 和关键技术选型

场景 B 是供电业务知识问答，技术路线是 RAG（检索增强生成）。一句话讲清楚它的思想："考试时翻开书找答案，而不是把书背进脑子。"动手前先理解它的核心链路和选型，这样你写启动提示词时才能把技术说清楚。

🔗 RAG 的核心链路
知识文档md/docx/pdf → 分块按「条」切 → 向量化bge-m3 → 向量库Chroma → 用户提问 → 检索 top-K → LLM 生成DeepSeek → 答案+来源
为什么是 RAG，不是微调、不是纯关键词搜索？ 知识文档会更新，RAG 只需重建索引、不用重训模型；RAG 答案天生带来源引用（哪份文件哪一条），可溯源、防幻觉；纯关键词搜索匹配不上自然语言（"电费算错了怎么退"和"电费差错核查与退补"有语义鸿沟）。RAG = "开卷考试"，是最适合供电业务问答的技术路线。
⚙️ 关键技术选型（为什么这么选）
组件选型为什么
向量数据库ChromaPoC/MVP 首选，pip install 一行、API 简单、十分钟跑通；FDE 的决策逻辑——不为 100 份文档搭 Milvus 集群。生产大规模才换 Milvus/pgvector
Embeddingbge-m3（走 API）中文 RAG 的常见起点：1024 维、支持 8192 token、三重检索（Dense+Sparse+ColBERT）；走 API 免运维，课堂合成材料可在课堂批准环境使用公网服务。生产高精度可换 Qwen3-Embedding-8B
生成模型DeepSeekRAG 场景幻觉低、能可靠引用文档内容；国产开源、契合政企数据约束
分块按「条」切知识文档天然按「条」组织，每条一块、条款号保留——引用粒度对齐"第X条"，与验证集零转换。固定长度会切断条款号，不推荐
检索Dense 余弦 + top-5条款语义清晰、问题规范，基础检索够用；混合检索/重排序属于"发现问题再升级"，不一次堆满
✅ 这是 PoC 简化版：生产级 RAG 还有专业文档解析、512 token 分块与重叠、混合检索 + 重排序、RAGAS 三维评估等能力——本实操先跑通基础链路，学有余力再按"哪一类查询表现差就加对应那一项"的原则升级。
🔴 红线提醒：数据不出内网（数据包 脚手架/AGENTS.md 第 1 条）。课堂用的全部是教学合成的虚构材料；任何真实客户诉求、用电信息、知识文档内容不得发往外部网络服务。注意：这条红线写在数据包的硬约束里，启动提示词里只写一句"数据不出内网"，不抄十一条原文。

🔑 场景 B 特有的把关点（都围绕 RAG 的特性）
  • 切块策略：按「条」切块、条款号随块保留；文档末尾的"负责解释／施行／有效期"这类程序性条款对所有问题都呈中等相似度，会污染检索，建索引时建议过滤。
  • 检索数量 top-K：太少答案不全，太多噪声大；实测 top-5 配合程序性条款过滤，效果稳定。
  • 检索不到怎么办：绝不能编——必须明说"知识库中未找到，建议咨询人工"。拒答靠两道防线：相似度阈值（进门槛）＋ 提示词约束模型判断兜底。
  • 来源引用格式：答案要显示"文件名 + 条款号"，这是可溯源的底线。
  • 建索引后必须抽查检索：对每条验证集问题输出 top-K 排名，人工扫一眼目标条款在不在前几；不抽查直接验收，目标条款可能被程序性条款挤掉，首轮必失败。
⚠️ 这五件事是 autoplan 的拍板点，不是启动提示词的内容。它们由 autoplan 环节暴露选项、由你拍板、结论写回 SPEC；启动提示词里只在【约束】块写一句"无证据必须返回 not_found，不得编造条款号或数值"。
为什么"答案可追溯"是这个场景的命门？用电客户问供电业务，AI 答错了，坐席和平台要负责。答案能溯源到"某指引 第十一条"，客户可以去核对，坐席也能说"这是按文件规定来的"——这就是周主任要的"免得坐席背锅"。

来源锚定：.docx / .pdf 两条按原始文件名锚定（如 岭湾电力供电服务规范与服务承诺（教学合成版）.docx 第十四条）。因此来源 metadata 要同时保留 source_file（原始文件名）与 normalized_file（解析后的检索文件名），验收按 source_file + article 严格比对。这一条属于手册与 spec 环节的验收细节，提示词里不展开。
⚙️ 验收命令（由手册与 qa 环节执行，不写进启动提示词）
python 验收\evaluate.py --task all --impl stub python 验收\evaluate.py --task all --impl src python 验收\evaluate.py --task all --impl api
判据：--impl stub 必须先跑通（证明工具口径与样本正常，排掉"环境问题"与"实现问题"的混淆）；--impl src 是本次交付物的成绩；--impl api 用于对照"在线模型直连"与你的实现差在哪。三条跑完，把答案准确率、来源可追溯率与库外拒答结果记进 qa-report.md。
提示词里写什么：只写验收口径的数字（答案准确率 ≥80%、来源可追溯率 ≥90%、库外必须拒答），命令本身不写。
环境准备：RAG 比分类器多了两样东西——向量库和embedding 模型。在本目录建一个独立虚拟环境（不要复用之前的项目环境），装向量库（推荐 chromadb）与 embedding 服务（走 API，如 bge-m3，把 base_url 与模型名写进 .env）。验证标准：装完必须实际 import + 调用、打印出向量维度（如 1024）才算准备好——pip list 显示"已安装"可能是环境泄漏的假象。

实验三 · 驱动指令

驱动指令版：怎么让 Agent 按流程跑

和场景 A 一样，用 5 条驱动指令（每条一行）把八环节的流程纪律焊进 Agent 的执行里。你写好启动提示词后，把两者合起来交给 Agent：

/office-hours 我是一名 FDE 团队（Delta 角色），需要启动岭湾电力客户服务平台场景 B 的施工。 【在这里粘贴你写好的启动提示词，包括 6 个短块：背景 / 要做什么 / 技术选型 / 数据现状 / 验收口径 / 约束】 请以 gstack 标准开发流程执行本次开发，严格遵守以下要求： 1. 依次走完 8 个环节：office-hours → spec → autoplan → 施工 → review → qa → ship → retro，不跳步、不简化。 2. 每个环节都要产出对应文件并落盘当前目录，在回复中列出文件名与位置。 3. 走完一环、进入下一环之前先停下来向我汇报，等我确认后再继续（禁止一口气跑完）。 4. 拍板点（验收口径／门槛／兜底）列出选项与利弊并给出建议，最终由我拍板；拍板结论写回 SPEC。 5. 现在从 office-hours 开始。
重点看驱动 3、4："一环一停"和"拍板点列选项等你选"——这两条决定了你后面还有没有把关的机会。没有它们，Agent 可能一口气跑完八环，你失去所有中途纠偏的机会。场景 B 的五个拍板点（切块策略、检索 top-K、检索不到怎么办、来源引用格式、建索引后抽查检索）由 autoplan 环节暴露，不写进启动提示词。
