实验四 · 工单分级路由工作流 · 启动提示词向导

你的任务：把实验一《解决方案框架》场景 C 的部分，翻译成一段能让 Agent 开跑的启动提示词。
这次和场景 A／B 不同——场景 C 输出之后还要继续"做事"。先认识固定路由工作流和技术选型，再一步步填，最后点"生成"拼装完整提示词。

路由工作流 · 技术背景

先认识固定路由工作流与技术选型

场景 C 是供电服务工单智能分级路由，技术路线是 LLM 驱动的固定路由工作流（Routing Workflow，Agentic Workflow 的一类）——它不是会观察后重新规划的动态 Agent，而是"分类之后按预设分支执行动作"的工作流，是理解 State、Node、条件分支与自动化边界的入门台阶（动态 Agent 在实验五中展开）。动手前先理解它和场景 A／B 的本质区别、以及关键技术选型，这样写启动提示词时才能把技术说清楚。

路由工作流和场景 A／B 有什么本质区别？
· 场景 A 分类：一份诉求 → 一个类别（贴完标签就结束）
· 场景 B 知识问答：一个问题 → 一个带来源的答复（查完文档就结束）
· 场景 C 路由工作流：输出之后还要继续"做事"——判出"跨专业协同"后继续查专业职责库、生成处理意见、决定要不要转人工。
这就是"分类之后执行预设动作"——分支与动作在开发时已确定，路径可预先枚举。它还不会观察中间结果后重新规划；那种能力属于实验五的受控协同 Agent。
🔗 工单分级路由工作流的分支动作
工单进来客户诉求 → 分级模型判断档位 → 路由条件边分流 → 咨询自动答复 → 跨专业协同查专业职责库 → 敏感转人工真暂停
为什么用路由工作流，而不是纯分类器？ 分类器只输出"这工单是跨专业协同类"就结束了。而路由工作流输出标签后还能继续：查专业职责库、生成工单草稿、决定转不转人工——"分类之后还能做事"。
为什么此时还不需要动态 Agent？因为三档分支和每档动作都已知，路径可以预先枚举。做错代价大不大、路径能不能枚举、要不要根据中间结果换工具——这三问决定你真正需要的是 Workflow 还是动态 Agent。这也是本实验的验收必须验证"判档 + 动作"双重原因。
⚙️ 关键技术选型（为什么这么选）
组件选型为什么
编排框架LangGraphWorkflow／Agent 编排事实标准：State／Node／Conditional Edge 三概念就够构建固定路由；内置 Checkpointing（崩溃恢复）、interrupt()（人机协同）等工程能力

gstack · 是什么

先认识 gstack

gstack 是团队统一使用的 AI 开发工作流框架，安装在编码 Agent 里，用 /命令 调用。它把一次 AI 开发迭代组织成八个环节的流水线，上一环的产出是下一环的输入，一环都不能跳：

office-hours
要不要做 → spec
死磕边界 → autoplan
决策拍板 → 施工
做出来 → review
找隐患 → qa
测体验 → ship
收尾 → retro
复盘
和前几轮一样：你不一步步教 Agent 写代码，而是把启动提示词交给它，让它按这八环节自动跑，你在每个 checkpoint 把关。这八环节就靠下面生成的"驱动指令"约束它。

贴出前自查 · 7 个问题

贴出前，逐条自问（答不上"能"就回去补）

这 7 个问题不是考题，是防止你把提示词交给 Agent 之后才发现漏项。逐条对照，回头改。

  • 换一个完全不了解项目的人来读，他能知道 我在为谁、做什么 吗？
  • 他能不能知道 输入是什么、输出是什么？
  • 他能不能知道 为什么是固定路由工作流，而不是纯分类器或动态 Agent？
  • 他能不能知道 数据是什么情况（工单样本与专业职责库连数据给出、敏感清单是什么、怎么用）？
  • 他能不能知道 做出来怎么算成功（尤其敏感件零漏判）？
  • 他能不能知道 有什么红线（不做的事、不碰的数据、不许假装的暂停）？
  • 他能不能知道 按什么流程跑、产出什么？
