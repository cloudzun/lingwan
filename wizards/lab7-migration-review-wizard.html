实验七 · 复盘真实项目（可选） · 复盘向导

课程结束后的无编号可选挑战：把你在岭湾课程主线里学会的 FDE 理念、流程和判断框架，迁移到自己的真实项目上，完成拆解、复盘与决策层汇报。
框架不变，项目换成本人的真实工作。只使用 Echo（主责判断）与 Delta（主责施工）两个角色，不新增第三种学员角色。
模板不预填答案——基于你的真实证据一栏栏填。不影响主线结业；没有合适真实项目的学员，完成主线即可。

AI 可以用，但关键判断必须是你自己下：AI 可以帮你整理材料、按证据状态归类、扮演红队质询、检查汇报结构；但"客户真正的问题是什么""这个风险能不能接受""值不值得继续投"——AI 替不了 Echo 和 Delta。
三部分 + 汇报 · 自由切换

复盘真实项目工作台

Part 1 · Echo 重走 Discovery（约 60 分钟）

Echo 主责判断：整理事实底账 → 四类失败模式 → 四层决策链 → 重新定义问题 → 拆场景选型。产出你真实项目的解决方案框架，并给每个字段标注证据状态。

💡 讨论指引 · 红队质询问题卡（卡住时展开）▶
事实Q-E1 这个"真实问题"是你推断的，还是客户确认的？
能区分事实与判断，并指出哪一句是客户原话。
价值Q-E2 如果不再做这个项目，客户的具体损失是什么？
讲出具体业务损失，不能只说"效率低"；还要说清这个价值几周能验证、用什么证据。
选型Q-E3 为什么用这个技术路线？为什么不用更复杂的？
三问必答：为什么选它、为什么不用更复杂的、如果不用 AI 是否反而更合适。
风险Q-E4 四类失败模式里哪一类最致命？证据在哪？
数据不可用 / 业务不配合 / 合规卡住 / ROI 说不清——客户不会主动告诉你，你得自己读出来。
📋 输出物 1：真实项目解决方案框架
复用实验一的框架结构；每个字段标注证据状态（已实测／客户确认／当前假设／待获取）。
判断项内容证据状态
1 客户 / 被服务部门
2 客户原始表达
3 当前业务流程
4 已有系统 / 原型
5 已掌握数据
6 已有成败 / 停滞
技术路线仍按课程逻辑：一次调用可以解决 → Prompt 或分类；必须查询资料并提供来源 → RAG；路径稳定、规则可以预先枚举 → Workflow；需要根据中间结果追问／选工具／调整下一步 → Agent；需要改变模型稳定行为且数据充分 → 再评估微调。若不用 AI 反而更合适，就诚实写出来。
Part 2 · Delta 重审 Prototype / Build / Scale（约 60 分钟）

Delta 主责施工：判断项目实际阶段 → 按方案类型检查证据 →（必要时）最小验证设计 → 真实环境适配／业务闭环／人工接管／FDE 撤出差距。

💡 讨论指引 · 红队质询问题卡（卡住时展开）▶
阶段Q-D1 现在是什么阶段？凭什么？
有代码 ≠ 已证明原型价值；有页面 ≠ 已进入 Build；已经上线 ≠ 客户能够接管。
选型Q-D2 你这个"Agent"是动态的，还是固定 Workflow？
诚实区分，不为了好看硬叫 Agent；如果是固定 Workflow，就写它是固定 Workflow。
数据Q-D3 演示数据和真实数据差多少？
列出差异，并说明差异会如何影响你的结论。
接管Q-D4 客户离场后，谁用、谁维护、谁升级？
讲清运营责任归属与 FDE 撤出条件；只有你的电脑能跑，就还没完成交付。
📋 输出物 2：Delta 复盘表
阶段判断 + 逐类证据 + 真实环境差距 + 人工接管 + 下一 Gate。
子场景当前阶段已验证证据未验证假设真实环境差距 / 人工接管 / 下一 Gate
Part 3 · Echo + Delta 双视角收口（约 30 分钟）

共同判断：问题是否找对、价值是否成立、原型是否成立、能否进真实环境、什么能力值得沉淀、下一阶段决策。

💡 讨论指引 · 红队质询问题卡（卡住时展开）▶
决策Q-G1 Echo 说值、Delta 说还远——谁对？
两个视角互补，合起来要能点破最硬的那条差距。
沉淀Q-G2 凭什么说这项能力可以带走？
六问必答：从哪识别、去掉什么客户特定内容、抽象成什么、集成到哪里、在哪个第二场景验证、谁维护。
决策Q-G3 为什么是 Go，而不是 Continue Pilot？
给具体风险边界；"演示能跑"不等于"生产能接管"。
📋 输出物 3-1：双视角验收
Echo：问题是否找对、价值是否成立、组织是否愿意采用；Delta：原型是否成立、能否进真实环境、客户能否接管。
视角判断内容互补点 / 最硬差距
Echo（问题 / 价值 / 采用）
Delta（原型 / 落地 / 接管）
共同结论
📋 输出物 3-2：能力沉淀候选清单（四层）
四层：内容（换客户必须全换，通常不留）／工具（接口契约）／Workflow-Agent 机制（路由、追问、人工暂停、停止条件）／业务语义（对象、关系、状态、动作、治理）。
候选抽象后的通用能力层次第二场景验证维护人

决策：Go（证据足够可进下一阶段）／Conditional Go（可推进但必须先满足明确条件）／Continue Pilot（继续试点收集证据）／No-Go（价值或风险不成立，停止或返回 Discovery）。

决策层汇报 + 导出（约 30 分钟）

面向扮演客户侧决策层／操作层／技术层／监管层的听众。汇报 8 分钟 + 质询 7 分钟。Echo 讲问题与价值，Delta 讲方案与落地，共同提出结论（10 段结构）。

💡 讨论指引 · 红队质询问题卡（卡住时展开）▶
质询Q-R1 证据真实吗？哪些结论只是当前假设？
说不出证据的结论，先标成假设再说。
质询Q-R2 谁承担人工和业务责任？客户能否接管？
接管责任、运营维护、FDE 撤出条件。
质询Q-R3 为什么应该继续或停止？哪些能力值得带走？
用证据回答，不凭感觉。
质询Q-R4 出了数据问题谁负责？有没有泄露客户秘密、个人信息或凭据？
保密红线：API Key、密码与 Token、客户生产数据、身份证号／手机号等个人信息、未公开合同、内部网络拓扑、未经授权的源码和日志，一律不得展示。
🎤 输出物 4-1：决策层汇报稿（10 段结构）
Echo：1 客户及项目背景 · 2 表面需求 vs 真实问题 · 3 场景拆解与优先级 · 4 价值证据与采用风险；Delta：5 技术路线与选型理由 · 6 原型证据或最小验证设计 · 7 真实环境差距、接管与下一 Gate；Echo + Delta：8 能力沉淀候选 · 9 Go / Conditional Go / Continue Pilot / No-Go · 10 请求批准的资源或行动。
📋 输出物 4-2：证据状态与匿名化声明
所有信息按四类标记：已实测（有运行结果、数据或用户行为支持）／客户确认（客户或业务负责人明确确认）／当前假设（合理但尚未验证）／待获取（缺少关键资料或数据）。
红线：如果没有任何真实证据，只能把项目标为"项目构想"，重点设计验证计划，不得声称已经完成真实验证；不得伪造没有发生过的施工过程——只做复盘时，把已有证据映射到 gstack 八环节（office-hours 该不该做 / spec 边界与失败路径 / autoplan 谁拍板 / build 是否忠实需求 / review 哪些隐患发现太晚 / qa 是否用真实用户与边界验证 / ship 是否可交付可复现 / retro 哪些经验值得带走）。
